# ESP32-S3 固件工程化重构方案

更新日期：2026-10-28。

本文记录重构的目标、原始问题、架构决策和长期约束。首轮实现与第二轮收敛已落地并通过本地构建与主机测试，硬件验收尚未完成。阶段进度和下一步任务见 [实施路线](firmware-roadmap.md)；构建命令、配置协议、资源预算和操作步骤见 [固件开发与验收](firmware.md)。

## 1. 目标与范围

目标是让固件能够长期增加内容字段、交互方式和设备管理能力，同时保持修改范围、资源责任、故障表现和验证方法清晰。

长期仅支持 ESP32-S3，沿用 ESP-IDF、FreeRTOS、LVGL 和纯 C 功能模块，`main.cpp` 保留为唯一 C++ 入口。正式构建入口为 PlatformIO，使用固定版本的平台和依赖。

本轮范围覆盖固件、管理页面、资源构建脚本、组件声明、主机测试和 CI 配置。Go 后端的业务扩展单独安排。保持现有分区布局和硬件接线，不假设板上存在 PSRAM。

长期验收标准：

- 增加内容字段不需要修改屏幕驱动。
- 增加手势不需要修改 HTTP 客户端。
- 更换显示硬件不影响评分和配置逻辑。
- 升级固件保留可迁移的用户配置。
- 网络、协议、存储和显示故障可以通过状态、错误码与测试定位。

## 2. 重构前的问题与改造方向

以下描述是重构前的代码行为，作为方案依据，不代表当前实现仍存在相同问题。

| 原始问题 | 工程影响 | 改造方向 |
| --- | --- | --- |
| 显示任务同时处理 HTTP、手势、评分、倒计时和动画 | 慢请求阻塞输入；修改交互影响网络流程 | 应用状态机与网络任务分离，使用单调时间 deadline |
| 获取 next URL 时隐式更新全局标题、时间和条目 ID | 异步化后容易对错误条目评分 | 完整内容模型，当前内容与候选内容分开，评分显式传入 ID |
| 同一配置在 next 中表示完整 URL，在评分中表示根地址 | 评分路径拼接错误 | 统一 `api_base_url` 与 `device_id`，集中构造 URL |
| 显示模块包含引脚、SPI、LVGL、页面、字体和标题动画 | 所有权不清晰，页面切换依赖隐含刷新约定 | 驱动、页面、banner 和解码边界分离，唯一 UI 所有者 |
| WiFi 获取 IP 后停止连接流程，后续断线无法按原逻辑恢复 | 长期在线能力不足 | 异步连接服务、退避重试与救援 AP |
| 固件版本变化清空配置 namespace | 频繁迭代导致凭证丢失 | 固件版本与配置 schema 分离，集中迁移和保存 |
| HTTP body 仅接收一次，JSON 手工搜索和拼接 | 分片、转义与非法输入容易处理错误 | 有界完整接收，使用 cJSON 解析和序列化 |
| API 自定义 headers 无条件用于图片下载 | API 凭证可能发送给外部图片主机 | API 与图片的 header 策略分开 |
| 图片失败降级为纯色后统一返回成功 | 难以区分正常无图与下载、解码故障 | 结构化错误和独立降级结果 |
| 递归收集所有库源码，通过缓存时间选择 LVGL | 组件依赖失去约束，构建依赖本机缓存状态 | 显式 IDF 组件，固定依赖路径与版本，关闭重复库发现 |
| 测试仅有脚手架，运行状态信息不足 | 回归与长期内存问题难以判断 | 主机逻辑测试、故障注入、资源诊断与板级验收 |

保留的基础机制包括 GPIO 中断到队列的交接、ESP-IDF WiFi/IP 事件、TJpgDec 分块输出、字体分区 mmap、字形缓存释放和 NVS 基础封装。

## 3. 模块边界

| 边界 | 当前实现 | 责任 |
| --- | --- | --- |
| 启动入口 | `src/main.cpp` | 启动纯 C 控制器，处理启动失败 |
| 应用控制 | `lib/app_controller` | 当前内容、候选内容、请求编号、交互状态、计时与重试策略 |
| 输入采集 | `lib/button_input` | GPIO 消抖、时间戳队列、丢失计数；手势语义由 `app_state` 解释 |
| 网络调度 | `lib/network_worker` | 顺序执行 API 与图片下载，向应用交接结果 |
| 后端协议 | `lib/backend_client`、`lib/content` | 内容模型、JSON 校验、URL 构造、显式条目评分 |
| HTTP 传输 | `lib/http_transport` | 超时、状态码、下载边界、完整性和 header 策略 |
| 内容展示 | `lib/content_view`、`lib/jpeg_decoder` | 将内容与 JPEG 转为可显示结果，解码通过像素回调输出 |
| 显示与字体 | `lib/display_driver`、`lib/ui_animation`、`lib/banner`、`lib/cjk_font` | 板级驱动、LVGL 页面、底栏、标题动画和字体缓存 |
| 配置服务 | `lib/app_config`、`lib/nvs_manager` | 默认值、设备标识、校验、迁移、完整配置持久化、加载状态与降级恢复、生效快照 |
| 连接服务 | `lib/wifi` | 异步连接、退避、救援 AP 与受保护的状态快照 |
| 管理协议 | `lib/http_server`、`data/www` | 管理请求适配、配置页面、静态资源和诊断接口 |

原方案中的独立 `image_loader` 责任由 `network_worker` 调用 `http_transport` 承接；LVGL 适配目前保留在 `ui_animation` 内，板级 SPI 已提取到 `display_driver`。后续是否继续拆分，以依赖复杂度和实测问题为依据。

## 4. 并发与资源所有权

采用一个应用/UI 任务和一个网络 worker，复用 ESP-IDF 默认事件循环及 HTTP server 任务。功能模块不分别创建线程。

必须保持以下约束：

1. LVGL、屏幕、字体和 banner 缓存只由应用/UI 任务操作。
2. 网络 worker 只处理协议和数据，不调用显示接口。
3. JPEG 缓冲通过结果队列交接，接收方负责在渲染、替换或丢弃后释放。
4. 每个网络任务携带 request ID；过期结果丢弃并释放资源。
5. 评分携带用户操作时的 item ID，获取候选内容不会改变评分对象。
6. 评分与反馈期间延迟切换候选内容；离线时保留已显示内容。
7. 跨任务使用受保护的快照或队列，不暴露内部可写状态指针。

轮播、双击窗口、评分超时和反馈停留使用单调时间及 deadline。动画帧率不能决定业务时间。早期通过请求超时与结果失效管理生命周期，暂不引入复杂的 HTTP 中途取消。

JPEG 解码仍在 UI 任务同步执行，周期性让出 CPU 不能替代输入事件消费。是否实现可暂停解码或分批调度，需先测量最长处理延迟。

## 5. 数据、配置与管理协议

`content_item_t` 统一保存条目 ID、标题、发布时间和图像 URL；解析先验证候选对象，成功后再交给应用。没有评分 ID 的内容允许展示，评分时明确失败。

配置区分三个概念：编译期默认值、持久化的 `saved` 配置、启动后正在使用的 `active` 配置。固件版本用于发布标识，配置 schema 用于迁移；保存后重启生效。

整份配置存入单个 NVS 值，传播写入及 commit 错误，避免关联字段分别保存产生部分更新。标准旧 next URL 拆解为根地址与设备 ID；无法可靠识别的合法地址完整保留并提示修正。

配置加载结果是一个显式状态而不是布尔值：读取成功、首次生成、旧键迁移、显式保存，以及损坏内容、旧值不合法、旧地址无法识别、底层读取失败、存储不可用四类降级。任何降级都保留原始 NVS 值，以无凭证默认配置开放配网入口，只有显式保存才覆盖，状态经 `app_config_get_status()` 和 `/api/status` 可观测。诊断与恢复共用同一入口，避免“配置坏了就停在错误画面”而无法远程修复。

设备标识只由单一来源决定：页面或旧 URL 提供的显式标识原样使用且不被固件改写；首次启动没有可继承标识时由芯片 MAC 生成，并随首次配置持久化，因此多台设备不会共用编译期测试身份。

管理 HTTP 路由负责有界接收、解析、调用服务和返回响应。重启在响应完成后由应用安排；静态文件使用小缓冲分块发送。WiFi 密码及自定义 header 值不进入日志，API 凭证不用于外部图片下载。

当前明确拒绝重定向。若后续需要图片重定向或图片鉴权，应先定义允许的主机、跳转次数和凭证附加规则，再实现支持。

## 6. 显示与资源策略

保留直接绘制 JPEG、局部叠加标题和底栏的方式，先落实单任务所有权与刷新顺序。320×240 RGB565 单帧约 150KiB，全屏双缓冲约 300KiB，不作为默认方案。

轮播进度放在 banner 左右分栏之间的竖线上，底部 2px 状态条只用于评分和提交结果；模块记录当前内容，仅在内容变化或被整屏刷新、评分条、结果条覆盖后重写，避免每帧重复相同的 SPI 写入。被其他内容覆盖时必须显式失效，不能依赖“每帧都重画”。

保持分块 LVGL 缓冲、逐行 JPEG 输出、字体文件 mmap 和有上限的字形缓存。LVGL 使用系统堆分配；静态 RAM 减少不等于总运行内存等量减少。

故障处理需要同时说明可见结果和原始原因：正常无图、下载失败降级、解码失败降级、API 失败、存储失败分别可观测。资源预算包括响应大小、图片尺寸、队列深度、任务栈及动态缓冲生命周期。

## 7. 构建与验证策略

构建只保留 `esp32s3` 环境，固定经验证的平台与 LVGL 版本，保留 `build_unflags = -fuse-cxa-atexit`。不手工编辑生成的 `sdkconfig.esp32s3`。资源脚本通过 IDF 官方解析器读取分区表，校验大小与烧录地址。

组件声明显式列出源文件和依赖，关闭 PlatformIO LDF，避免重复编译。历史 `image_fetcher` 和 `rss_reader` 已从源码树删除，构建检查改为验证 `lib/` 下每个注册组件都进入构建。正式支持 PlatformIO；原生 `idf.py` 的资源与烧录链路仍未验收。

验证分为构建及资源检查、主机逻辑与故障测试、真实 HTTP/TLS 联调、板级交互与恢复、长时间运行。各层单独记录结果，主机测试不能代替后续层级的验收。

## 8. 持续迭代原则

新增功能先确定状态、数据和资源的所有者，再扩展接口。纯逻辑优先通过虚拟时间和故障注入验证；硬件薄封装通过适当的板级检查验证。

后续变更按可独立验收的范围推进，涉及协议、配置 schema 或资源格式时记录迁移及回退条件。预取、多任务显示、缓冲复用和更换渲染方式均需要测量依据。待办优先级和阶段退出标准统一维护在 [实施路线](firmware-roadmap.md)。
